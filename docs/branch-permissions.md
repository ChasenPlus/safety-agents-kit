# 分支与工具权限矩阵

每个分支只挂自己真正用得上的服务。挂多了除了多占进程，还会让模型在无关工具上乱试。

图例：`●` 必须 / `○` 条件触发 / `-` 不需要

| 分支 | sak-fs | sak-rag | sak-private | sak-crawler | sak-report | sak-excel |
|:---|:--:|:--:|:--:|:--:|:--:|:--:|
| A 条款检索与判定 | ● | ● | ● | ○ | - | - |
| B 巡查检查报告 | ● | ○ | ○ | - | ○ | - |
| C 制度修订起草 | ● | ○ | - | - | - | ○ |
| D 标准库管理 | - | ○ | - | ● | - | - |
| E 现场工作包生成 | ● | ● | ● | - | - | - |
| F 专项方案编制 | ● | ● | ● | - | - | - |
| G 写材料发文 | ● | - | - | - | ○ | - |
| H 定责考核与台账 | ● | ○ | ○ | - | - | ○ |

条件触发的含义：

- **A→crawler**：A 让 D 下载标准时，子代理继承调用方的工具配置，所以 A 也要挂 crawler。
- **B→rag**：只在需要查「这份文件涉及哪些制度」「清单里有没有这条」时用。
- **B/H→private**：B、H 自己不核验 R11，但调用 A 时子代理要用到 `check_coverage`。
- **C→rag**：只在按制度编号定位清单条目时用，不做条款判定。
- **C/H→excel**：台账直读/回写；若改用 `skills/excel-ledger-writer` 的脚本，可以不挂。
- **D→rag**：下载转换完成后入库。
- **G→report**：只有用户明确要求出正式 Word 报告时才用。

## 跨分支调用

| 调用方 | 目标 | 典型场景 |
|:---|:---|:---|
| B | A | 每个问题都要有依据，B 向 A 要条款原文 |
| B | H | 需要定责/考核时 |
| E | F | 现场工作包需要配套专项方案 |
| G | B | 汇报材料需要引用检查发现 |
| H | A | 缺口判定要条款依据 |
| A | D | 本地没有该标准，需要下载入库 |

CLI 里的写法：

```bash
sak handoff -b A "查 GB 50194-2014 第 8 章对配电箱漏电保护的要求" > /tmp/task.md
```

把输出整体交给子代理（或另一个 `sak run` 进程）即可，它已经带上完整的分支提示词和返回格式要求。

MCP 宿主里的等价工具：`server/agent_switch` 的 `get_handoff_packet(branch, task)`。

## 为什么不合并成一个「万能智能体」

早期版本就是单一大提示词，实测两个问题：

1. **token 开销**：不管问什么，八套规则的细节每轮都要加载；
2. **路由不可靠**：让模型自己判断「这条消息该走哪个功能」，误判率明显高于用户显式选分支。

拆成八条后，每次只加载正在用的那一条，切换成本交给用户，反而更稳。
